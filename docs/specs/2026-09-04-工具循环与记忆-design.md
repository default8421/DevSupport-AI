## 1. 为什么这么设计

### 1.1 现状核实结论

代码库里注册了 10 个工具并生成了 OpenAI function-call schema，但 `registry.openai_tools()`
**从未被任何代码调用**。真实执行路径是：

```
意图分类 → 查 ROUTE_MAP 静态表 → 进专家 Agent → Agent 内部硬编码顺序 execute() 固定工具
```

模型从头到尾没有参与过工具选择，也没有参与过参数构造。所以"完善工具调用能力"的起点不是
"再加几个工具"，而是"是否引入模型决策"。

### 1.2 调研结论：不要做全自主 ReAct

多份生产实践资料在这一点上一致：

- 客服 Agent 应采用**确定性流程 + LLM 只填参数**；"LLM 自主规划路径"被列为上不了线的做法。
  把全部工具塞进 prompt 会导致 token 膨胀且**选错工具率超过 30%**。
- 模型是**不可信的语义组件，不是授权引擎**。鉴权、目标解析、策略、确认、幂等必须由服务端确定性拥有。
- **RAG 证据不能授予权限；记忆只是上下文，不能创造权限。**
- LLM 输出与任何写操作之间必须插入确定性校验节点。
- 每个工具需要熔断；连续失败 N 次应升级转人工。

对照本项目：确定性 LangGraph 骨架、工具超时与重试、高风险工具拦截、租户隔离**都已具备**；
缺少的是**参数级模型决策**、**工具入参 schema 校验**和**熔断升级**。

因此本设计保留意图路由与并行专家 Agent，只在专家内部引入**有界**工具循环。

## 2. 架构：有界工具循环

### 2.1 新模块 `app/agents/tool_loop.py`

一个可复用的循环，供各专家 Agent 调用。每个专家**只能看到自己那 3–5 个工具**，
这是控制"选错工具率"的核心手段。

```python
@dataclass
class ToolLoopResult:
    content: str                # 模型最终文本
    invocations: list[dict]     # [{name, args, ok, duration_ms, error}] 供 trace 展示
    tokens: int
    degraded: bool              # 熔断触发，建议转人工

async def run(
    *, system: str, query: str, tool_names: list[str], ctx: ToolContext,
    model: str, history: list[dict] | None = None, max_iters: int = 3,
) -> ToolLoopResult
```

循环逻辑：

1. 组装 `messages = [system] + history[-4:] + [user]`
2. `tools = registry.tools_for(tool_names)`（新增 registry 辅助函数，按名字过滤且**恒定排除高风险**）
3. 迭代至多 `max_iters` 轮：
   - `r = await client.chat(messages, model=model, tools=tools)`
   - 无 `tool_calls` → 返回 `r.content`，循环结束
   - 有 `tool_calls` → 追加 assistant 消息，**并行** `asyncio.gather` 执行全部调用，
     每个结果以 `role="tool"` + `tool_call_id` 追加回 messages
4. 迭代用尽仍未给出文本 → 再发一次**不带 tools** 的请求，强制模型总结成答案

`client.chat()` 已支持 `tools` 并返回 OpenAI 风格 `tool_calls`（`llm/client.py:59-92`），无需改动。
assistant 消息可由 `tool_calls` 的 `id / name / arguments` 重建。

### 2.2 熔断

在循环内统计**连续失败轮次**：某一轮内所有工具调用均失败记一次。连续 2 轮全败即
`degraded=True` 并跳出循环，由调用方（专家 Agent）据此置 `need_ticket`，走既有的自动建单转人工。

这与已有的单工具级 `timeout` / `retries`（`registry.ToolSpec`）互补：前者防单点慢，后者防级联坏。

### 2.3 确定性入参校验（关键安全边界）

当前 `registry.execute()` **不校验入参**，模型给什么就直接传给工具函数。这是模型输出与执行之间
缺失的那道闸门。在 `execute()` 内、**高风险拦截之后、真实调用之前**加入针对 `spec.parameters`
的最小校验：

- `required` 声明的字段必须存在，否则直接返回 `{"ok": False, "error": ...}`，不进函数
- 出现 schema 未声明的字段 → 拒绝（不静默丢弃，避免掩盖模型错误）
- 基础类型检查（string / integer / number / boolean / object / array）

放在 `execute()` 而不是循环里，是为了让**所有调用路径**（含现存的硬编码调用）都受同一道闸门保护。
不引入 `jsonschema` 依赖，手写覆盖上述三项即可，避免为一处校验新增依赖。

### 2.4 各专家的工具可见范围

| 专家 | 可见工具 | 模型档位 |
| --- | --- | --- |
| `api_diagnostic` | `query_call_log`、`query_apikey_status`、`query_recent_call_stats`、`check_signature_canonical` | `model_for("diagnose")` → 大 |
| `billing` | `query_plan`、`query_usage`、`query_bill` | `model_for("billing_explain")` → 大 |
| `doc_rag` | 不变，RAG 仍硬编码在 Agent 内 | 不变 |

`doc_rag` 保持原样是刻意选择：把检索交给模型决策会新增一次 LLM 往返，而文档问答的
检索时机是确定的（进了这个 Agent 就一定要检索），模型决策没有收益。

高风险工具（`reset_api_key` / `change_plan` / `refund`）继续对模型完全不可见。

## 3. 新工具：待签字符串校验 `check_signature_canonical`

### 3.1 为什么不算 HMAC

`ApiKey` 表只存脱敏值（`models.py:66`，注释明确写"仅存脱敏值"），**没有 secret_key 字段**，
全库也没有任何 HMAC 实现。要真算签名，只能新增字段存明文密钥，或让用户把 Secret Key
贴进聊天框——后者正是知识库明令禁止的（`data/knowledge/02-鉴权与签名.md` 安全建议一节），
且脱敏层会把它当密钥打码，Agent 拿不到完整值。

另外文档里的伪代码本身规格残缺：`hmac_sha256(raw + "&secret=" + secret_key)` 只有一个入参，
而 HMAC 需要密钥与消息两个输入。照它实现必然与真实平台不一致。

**本工具改为校验"待签字符串的构造过程"**，不接触密钥，因此也完全绕开上述规格问题。

### 3.2 覆盖能力

知识库列出的 `SIGN_INVALID` 四条排查要点中，**三条不需要密钥即可判定**：

| 文档排查项 | 本工具能否判定 |
| --- | --- |
| 1. 参数严格字典序，无遗漏或多加 | ✅ 重排并逐字符 diff |
| 2. Secret Key 与 API Key 配对 | ❌ 需要密钥，输出中提示用户自查 |
| 3. 时间戳秒级、偏差不超过 5 分钟 | ✅ 位数判定 + 窗口判定 |
| 4. UTF-8 编码，未对 value 额外 URL 编码 | ✅ 检测 `%XX` 转义 |

### 3.3 接口

```python
{
  "name": "check_signature_canonical",
  "parameters": {
    "type": "object",
    "properties": {
      "params":        {"type": "object", "description": "业务参数键值对，不含签名本身"},
      "timestamp":     {"type": "string", "description": "用户使用的 X-Timestamp 原值"},
      "api_key":       {"type": "string", "description": "X-Api-Key，可为脱敏值"},
      "client_string": {"type": "string", "description": "用户自己拼出的待签字符串（可选）"}
    },
    "required": ["params", "timestamp"]
  }
}
```

`client_string` 缺失时（最常见情况，用户通常不会主动贴出自己拼的串）工具**降级但仍有用**：
跳过逐字符 diff，仍执行时间戳位数与窗口判定、URL 编码检测、误贴密钥检测，并返回
正确的 `canonical_string` 供用户自行比对。此时 `issues` 中追加一条
`{"code": "NO_CLIENT_STRING", "fix": "把你代码里拼出的待签字符串贴出来可精确定位到第几个字符"}`，
引导模型在下一轮追问——这也是有界工具循环相比一次性调用的价值：模型看到这条提示会自己决定追问。

返回结构化结果：

```python
{
  "canonical_string": "api_key=ak_****8a2f&idcard=***&name=***&timestamp=1718000000&secret=***",
  "sorted_keys": ["api_key", "idcard", "name", "timestamp"],
  "issues": [
    {"code": "TIMESTAMP_UNIT", "detail": "时间戳为 13 位毫秒级", "fix": "改用 10 位秒级"},
    {"code": "ORDER_MISMATCH", "detail": "第 2 个参数应为 idcard，实际为 name", "fix": "按 ASCII 升序重排"}
  ],
  "secret_checked": false   # 明确告知未做 HMAC 校验，避免误判为"签名正确"
}
```

### 3.4 安全约束

- 工具**永不接收也永不返回真实密钥**；`&secret=` 一律以字面量 `***` 占位。
- 入参中若出现名为 `secret` / `secret_key` / `sign` / `signature` 的键，**剔除并在 `issues`
  中告警**（用户误贴密钥的场景）。
- `canonical_string` 中各 value 在返回前经 `desensitize` 处理，防止身份证等 PII 原样回显。
- `secret_checked: false` 必须出现在返回中，且 Agent 的 system prompt 需明确要求：
  在未校验 HMAC 的情况下**不得断言"签名正确"**，只能说"构造过程无误，若仍失败请核对 Secret Key 配对"。

## 4. 记忆分层

### 4.1 已核实的问题

| 问题 | 证据 |
| --- | --- |
| 冷启动/TTL 过期后失忆 | `session.get_history()` 只读 Redis；MySQL 有完整对话却不回填 |
| 实体不落库 | `conversation.collected_entities`（`models.py:156`）建了列，代码从未写入 |
| 无跨会话记忆 | 键为 `mem:hist:{conv_id}`，仅会话级 |
| 无压缩 | 仅 `ltrim` 到 20 条，超出直接丢弃 |

（注：先前怀疑 `clarify` 与缓存命中绕过脱敏节点，经核实**不成立**——`clarify_question`
是硬编码常量，缓存写入的是已脱敏的 `final_answer`。无需修改。）

### 4.2 四项改动

**(1) MySQL 回填（修 bug）**

新增 `app/memory/store.py` 承担 MySQL 侧读写，保持 `session.py` 纯 Redis，职责不混。

`load_context` 改为：读 Redis → 若为空则从 MySQL `message` 表取最近 20 条按时序重建 Redis
列表 → 返回。冷启动与 TTL 过期都不再失忆。

**(2) 实体与意图落库**

`run()` 末尾写 `conversation.collected_entities` 与 `latest_intent`，用上已有的列。

**(3) 用户级长期记忆（跨会话）**

新表 `user_memory`：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int PK | 自增 |
| `tenant_id` | str(64) | **索引，且所有查询必须带上**，防跨租户泄漏 |
| `user_id` | str(64) | 索引 |
| `kind` | str(32) | `app_id` / `plan` / `recurring_error` / `endpoint` |
| `value` | str(128) | |
| `hits` | int | 出现次数，用于排序与"反复遇到"判定 |
| `updated_at` | datetime | |

唯一约束 `(tenant_id, user_id, kind, value)`。

**存的是结构化派生事实，不是自由文本**——这是刻意限制 prompt 注入面：
用户说什么都不会被原样存进记忆再回灌到 prompt，只有被识别为实体的值才会入库。

写入规则（每轮结束后执行，明确到键，避免实现时各写各的）：

| 来源 | 落成 `kind` | 说明 |
| --- | --- | --- |
| `entities["endpoint"]` | `endpoint` | 命中即 upsert，`hits+1` |
| `entities["error_code"]` | `recurring_error` | 命中即 upsert，`hits+1`；`hits>=2` 才在注入时称"反复遇到" |
| `entities["app_id"]` | `app_id` | 命中即 upsert |
| `billing` 专家返回的套餐名 | `plan` | 仅在该专家实际执行过时写入；同一用户只保留 1 条（先删后插） |

`request_id` **不入库**：它是单次调用的一次性标识，长期留存没有复用价值且会无限膨胀。
`http_status` 同理不入库。

读取：`load_context` 取该用户 `hits` 最高的前 5 条，拼成一行紧凑的 system 提示注入，例如
"该用户历史特征：常用 /v1/idcard/verify；近期反复遇到 SIGN_INVALID（3 次）；套餐 专业版"。
无任何记录时**不注入这行**，避免出现"该用户历史特征："后面空着的畸形 prompt。

上限硬性约束：**最多 5 条、每条 ≤ 60 字符**，避免长期记忆无声膨胀推高每轮 token。

Redis 侧加 `mem:user:{tenant_id}:{user_id}` 作缓存，MySQL 为权威。**键必须含 `tenant_id`。**

**(4) 滚动摘要压缩**

历史达到 `HISTORY_MAX`(20) 时，把最旧 10 条用小模型（`model_for("summarize")` 实为大模型，
此处显式用 `settings.llm_model_small`）压成一段摘要，存 `mem:summary:{conv_id}`，保留最近 10 条原文。
注入顺序：`[system] + [摘要] + [最近原文]`。

### 4.3 记忆的安全约束

摘要与用户级记忆都**派生于用户输入并会被重新注入 prompt**，因此：

- 写入前必须过 `desensitize.desensitize_text()`，防止用户贴过的密钥/身份证被记忆固化后回显。
- 记忆内容**仅作上下文，不得作为任何授权依据**。工具鉴权一律走 `ToolContext.tenant_id`
  这条服务端可信路径，绝不读记忆里的 tenant/user 值。
- 用户级记忆的所有读写都带 `tenant_id` 条件。

## 6. 可观测

- 工具循环的每次调用写入 `invocations`，经 `trace.step()` 落 `AgentTrace`，
  前端 `TraceFlow` 可展示"模型选了哪个工具、填了什么参数、耗时多少"。
  这是本次改动最有展示价值的部分：从"固定管线"变成"可见的模型决策过程"。
- `degraded=True` 需在 trace 中显式标记，便于统计熔断率。
- `registry.execute()` 已有 `tool_call_log` 落库（含脱敏），入参校验失败也要记一条
  `status="rejected"`，否则模型的参数错误会变成无声失败。

## 7. 测试

`pytest` / `pytest-asyncio` / `asyncio_mode="auto"` / `testpaths=["tests"]` 已在
`pyproject.toml` 配好，但 `tests/` 目录不存在，当前**零测试**。本次补齐：

| 测试 | 类型 | 依赖 |
| --- | --- | --- |
| 待签字符串构造与 diff（排序、缺参、多参、编码、时间戳位数与窗口） | 纯单测 | 无 |
| 误贴密钥被剔除且告警 | 纯单测 | 无 |
| `execute()` 入参校验：缺 required / 多余字段 / 类型错 | 单测 | 无（mock 工具函数） |
| 工具循环：无 tool_calls 即返回、多轮迭代、迭代用尽强制收尾 | 单测 | mock `client.chat` |
| 熔断：连续 2 轮全败置 `degraded` | 单测 | mock |
| 记忆回填：Redis 空且 MySQL 有数据时能重建 | 集成 | Redis + MySQL |
| 跨租户隔离：A 租户读不到 B 租户的 `user_memory` | 集成 | MySQL |

优先级最高的是**待签字符串**与**跨租户隔离**两组：前者是新功能的正确性核心（算错会理直气壮地
误导用户），后者是安全底线。

## 8. 明确不做

- 不移除意图路由，不做全自主 ReAct（§1.2）
- 不给 `ApiKey` 加密钥字段，不实现 HMAC 计算（§3.1）
- 除签名工具外不新增其他工具（平台健康状态、批量日志、接口规格等留待后续按需）
- RAG 不包装成工具，`doc_rag` 保持现状
- 不引入数据库迁移工具，不引入 `jsonschema` 依赖
- 前端不动（第 1 条独立进行）
