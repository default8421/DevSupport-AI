# 前端重构：对齐智能客服形态 设计文档

状态：已实现（2026-09-04）
决策依据：用户已确认三项 —— ① antd 6.6 + `@ant-design/x` 2.9；② 后端新增真实阶段事件；③ 全部页面重构 + 新增知识库页。

---

## 1. 目标与非目标

**目标**

1. 用 `@ant-design/x`（Ant Design 官方 AI 组件库）替换手写对话 UI，形态对齐主流智能客服。
2. 让**编排过程可见**：用户按下发送后不再面对数秒空白，而是看到真实的执行阶段。
3. 给刚完成的文档上传能力补上入口（现在后端有 4 个接口、前端零入口）。
4. 把 Agent 的工具调用链暴露出来（后端 `/api/traces` 已返回 `tool_calls`，现有 UI 从未展示）。
5. 修掉现有 SSE 解析器的正确性缺陷（见 §3.1），并让它可被测试。
6. 客户侧首屏体积**不高于**现状（现状 gzip 453 kB 单 chunk）。

**非目标**

- 不升级 React（保持 18.3；X 2.9 的 peer 只要求 `>=18`，已验证）。
- 不改造 LangGraph 编排逻辑本身，只在其上加阶段回调。
- 不做真流式（LLM token 直出）—— 用户已明确排除，理由是多 Agent 并行时"哪个 Agent 的 token 该往外吐"无法良定义。
- 不引入 Redux / Zustand（见 §6.2 的理由）。
- 不做移动端适配（当前是面向开发者的桌面工具）。

## 2. 已验证的技术前提

以下每一条都是实测结论，不是文档推断。探针工程 `/tmp/xprobe`。

| 项 | 结论 |
| --- | --- |
| 依赖矩阵 | `antd@6.6.2` + `@ant-design/x@2.9.0` + `react@18.3.1` 安装无 peer 冲突 |
| 组件可用性 | 计划使用的 12 个组件全部存在并渲染成功（`tsc --strict` 零错误，SSR 输出 12.7 kB HTML） |
| React 18 兼容 | 实测通过。控制台仅两条 SSR 专属警告（`XNotification` 需浏览器 API、`useLayoutEffect` 服务端不执行），纯客户端 SPA 不适用 |
| antd 5→6 | 项目现用的 22 个 antd 组件在 6.6.2 中**一个都没移除**；新增 `Splitter` / `Flex`，正好用于三栏布局 |
| 体积 | 仅 antd6+X+React = 864 kB raw / **279 kB gzip** |
| 体积基线 | 现有前端 = 1,423 kB raw / **453 kB gzip**，且是**单一 chunk、零代码分割** |

**两个 API 与文档不符之处**（实测校正）：

- `Think` 不接受 `items`，它是单个可折叠块：`<Think title="..." loading>{children}</Think>`。
- `FileCard` 是单文件卡片（`name` / `byte`），列表用 `FileCard.List`。它会把主名与扩展名拆成两个元素渲染。

**`@ant-design/x-markdown` 评估后不采用**：它直接 `import` CSS，在离线探针里无法验证渲染行为；而 `react-markdown` + `remark-gfm` 在本项目已跑通。为"流式 markdown 抗闪烁"这一边际收益引入未验证面不划算。若 §3.1 修复后仍有明显闪烁，再单独评估。

## 3. 后端改动（唯一的后端改动，务求最小）

### 3.1 先修 SSE 正确性缺陷

**现象**：打字机过程中 markdown 排版是乱的，等 `done` 到达才突然正常。

**根因**（已实测复现）：`sse_starlette` 的分隔符是 `\r\n`，且按 SSE 规范把**含换行的 data 拆成多个 `data:` 行**。而 `chat.py` 把 markdown 答案按 18 字符盲切，块内必然含换行；前端又按 `"\n"` 切分且不 trim。

```
后端发出：  event: token\r\ndata: **结论**：时间戳超窗\r\ndata: \r\ndata: 1. 校准时钟\r\n\r\n
原始内容：  '**结论**：时间戳超窗\n\n1. 校准时钟'
前端拼出：  '**结论**：时间戳超窗\r\r1. 校准时钟\r'
```

换行全部变成 `\r`，段落与列表结构被破坏。

**修法**：这是**前端解析器的缺陷**，不是后端的。后端行为符合 SSE 规范，不该改。前端新解析器必须：

1. 按 SSE 规范以**空行**分隔事件，而不是按行处理。
2. 同一事件内多个 `data:` 行用 `"\n"` **重新拼接**（规范要求）。
3. 行尾 `\r` 显式剥除（`\r\n` 与 `\n` 都要容忍）。
4. 跨 chunk 边界的半行/半事件正确缓冲。

这四条各自对应一个测试用例，见 §10。

### 3.2 新增 `stage` 事件（纯增量，向后兼容）

**事件顺序**：`stage*` → `meta` → `token*` → `done`（编排失败时以 `error` 收尾，见下）

`meta` / `token` / `done` 的 payload **一个字段都不改**。现有前端解析器对未知事件是静默忽略（`if/else if` 三分支），因此旧前端 + 新后端不会坏——这个向后兼容性是刻意保留的，便于前后端分开上线。

**payload**：

```json
{ "key": "api_diagnostic", "label": "正在分析接口报错", "status": "running", "order": 2 }
{ "key": "api_diagnostic", "label": "已定位为签名超窗", "status": "success", "order": 2, "duration_ms": 890 }
```

| 字段 | 说明 |
| --- | --- |
| `key` | 节点/工具标识，与 trace 的 `agent_name` / `tool_name` 一致 |
| `label` | 面向用户的中文文案，由**后端**给出（它才知道语义，如具体调了哪个工具） |
| `status` | `running` / `success` / `error` |
| `order` | 展示顺序，与 `trace.steps.step_order` 对齐 |
| `duration_ms` | 仅终态携带 |

前端遇到未知 `key` 时降级显示 `key` 本身，不阻塞。

### 3.3 实现方式

`chat.py` 现在是「先 `await supervisor.run()` 跑完 → 再开 SSE」。要在编排期间推事件，必须反过来：**先开 SSE，编排在后台任务里跑，通过 `asyncio.Queue` 把阶段事件喂给生成器。**

```python
async def event_stream():
    q: asyncio.Queue = asyncio.Queue()

    async def on_stage(evt: dict) -> None:
        await q.put(("stage", evt))

    async def orchestrate() -> None:
        try:
            result = await supervisor.run(..., on_stage=on_stage)
            await q.put(("result", result))
        except Exception as e:
            await q.put(("failed", e))

    task = asyncio.create_task(orchestrate())
    ...
```

三个必须处理好的点，否则会造成挂死或串话：

1. **客户端断开**：`EventSourceResponse` 在断连时会停止拉取生成器。必须在 `finally` 里 `task.cancel()`，否则编排任务成为孤儿继续烧 LLM 额度。
2. **编排异常**：现在异常会在 `await supervisor.run()` 处直接冒泡成 500。改成后台任务后，异常必须经队列传回，否则前端会永远等待。落库与 `done` 的既有语义不能变。

   **实现时的修正**：原计划是「经队列传回并重新抛出」。实际不能重新抛出——流已经开出去，响应头已发送，此时抛异常只会在 ASGI 层产生一条 "response already started" 的噪声日志，前端拿到的仍是一条无 `done` 的断流。改为：`log.exception` 记录完整栈（监控不丢），再发一个新增的 `error` 事件让前端能收尾。`error` 的文案是固定中文，**不带异常文本**——异常里可能有连接串、请求体。这一条同样是纯增量事件。
3. **落库时机不变**：assistant 消息仍在编排结束后、`meta` 之前落库。`meta.message_id` 依赖它，顺序不能动。

**阶段回调怎么到达各节点**：

- LangGraph 节点：`supervisor.run(..., on_stage=...)` 传入，各节点在 `trace.step()` 附近调用。
- 工具调用：挂到 `ToolContext.on_stage`（可选字段）。`ToolContext` 本来就是服务端可信上下文的载体、已流经所有工具，复用它比另开一条通道干净。`registry.execute` 在调用前后各发一次。

工具级阶段（"正在查询调用日志"）是信息量最大的部分，但涉及 `registry` 改动，作为独立任务排在节点级阶段之后，可单独放弃而不影响前面的成果。

## 4. 信息架构与布局

现状是「顶栏 + 6 个各自居中的窄页面」，是典型后台管理形态。智能客服的形态是**以对话为中心的三栏**。

```
┌────┬──────────────┬────────────────────────────┬──────────────┐
│    │              │                            │              │
│ 图 │  会话列表     │        对话主区             │  上下文面板   │
│ 标 │              │                            │  （可折叠）   │
│ 导 │ Conversations│  Welcome / Prompts（空态）  │              │
│ 航 │              │  Bubble.List               │  Tab1 引用来源│
│    │  + 新建对话   │  ThoughtChain（进行中）     │  Tab2 执行链  │
│ 56 │              │  Sender + Attachments      │  Tab3 关联工单│
│ px │   240px      │        flex: 1             │    320px     │
└────┴──────────────┴────────────────────────────┴──────────────┘
```

- **最左图标导航**（56px）：对话 / 知识库 / 文档 / 工单 /（内部）工作台 / 指标。图标 + Tooltip，用 antd `Icon` 组件替代现在的 emoji。
- **会话列表**（240px）：仅在对话路由下出现。其它路由这一栏让位给内容。
- **上下文面板**（320px，可折叠）：把现在散落在气泡里的引用/工单标签收拢，避免对话区被元信息挤占。

非对话路由（知识库/文档/工单/工作台/指标）用「图标导航 + 内容」两栏，内容区不再强制窄居中，充分利用宽屏——表格类页面现在被 `maxWidth: 1000` 限制得很局促。

## 5. 后端数据 → X 组件映射

这张表是重构的核心契约。左侧全部是**已存在**的后端数据，不需要新增接口。

| 后端数据 | 组件 | 说明 |
| --- | --- | --- |
| `messages[]`（role/content） | `Bubble.List` | 替代手写 Avatar+Card；三处重复的气泡逻辑收敛为一处 |
| `done.card`（conclusion/evidence/steps） | `Bubble` 的自定义 `messageRender` | 保留结构化卡片，但改为气泡内渲染 |
| `done.citations[]`（doc_title/section/score/**source**） | `Sources` | 新增能力。`source==="upload"` 标注「来自你上传的文档」——这正是子项目 #3 加的字段 |
| `stage` 事件（新增） | `ThoughtChain` | 编排进行中实时展示 |
| `/api/traces/{id}`.`steps[]` | `ThoughtChain` | 内部工作台的完整链路（替代 `@xyflow/react`，见 §9） |
| `/api/traces/{id}`.`tool_calls[]` | `ThoughtChain` 的嵌套内容 | **当前 UI 完全没展示**，后端早已返回 |
| `conversations[]` | `Conversations` | 会话列表，支持分组（今天/更早） |
| 空态 + 示例问题 | `Welcome` + `Prompts` | 替代 `Chat.tsx` 里硬编码的提示语 |
| `POST /api/documents` | `Sender` 的 `Attachments` | 对话内直接拖拽上传，落到当前租户知识库 |
| `/api/documents` 列表 | `FileCard.List` | 新增「我的知识库」页，展示 status/chunk_count/error_message |
| `POST /api/feedback` | `Actions` | 已解决 / 未解决 / 转人工，替代手写按钮 |
| 主题与国际化 | `XProvider` + `ConfigProvider` | 统一入口 |

**`documents.status` 的 UI 语义**（后端状态机 `pending→processing→published`/`failed`）：

| status | 展示 |
| --- | --- |
| `pending` / `processing` | `FileCard` 的 `loading`，文案「正在解析并建立索引」 |
| `published` | 正常，显示 `chunk_count` 个知识片段 |
| `failed` | 红色，**直接显示 `error_message`**（后端已保证它是可读中文，如"该 PDF 没有可提取的文本，可能是扫描件"） |

上传后需轮询状态。轮询仅在存在非终态文档时进行，全部终态即停止——不做无条件定时器。

## 6. 前端架构

### 6.1 目录结构

```
src/
  main.tsx              入口：XProvider + ConfigProvider + AuthProvider + Router
  app/
    routes.tsx          路由表（含 lazy 分割点）
    AppShell.tsx        三栏骨架
    IconNav.tsx         最左图标导航
  auth/
    AuthContext.tsx     用户态 + 登录/登出
    useAuth.ts
  api/
    client.ts           axios 实例 + 请求/响应拦截器（含 401 统一处理）
    sse.ts              SSE 解析器（纯函数，可测）
    chat.ts             chatStream
    endpoints.ts        其余 REST 封装
  types/
    api.ts              后端契约的 TypeScript 类型（替代满地的 any）
  features/
    chat/               对话（Bubble/Sender/ThoughtChain/Sources）
    knowledge/          我的知识库（上传/列表/删除）
    docs/               内置文档浏览
    tickets/            我的工单
    conversations/      历史会话
    workbench/          内部工作台
    metrics/            运营指标
  shared/
    useAsync.ts         请求态 hook
    Markdown.tsx        统一 markdown 渲染
    formatTime.ts       时间格式化（消除三处重复）
    priority.ts         优先级色板（消除两处重复常量）
```

### 6.2 状态管理：刻意保持轻量

现状问题不是"缺少状态库"，而是**没有统一的用户态与错误处理**：`currentUser()` 每次调用都 `JSON.parse` localStorage 且无异常保护；无 401 响应拦截，token 过期后除工作台外各页面表现不一。

因此只补两样：

1. `AuthContext` —— 用户态读一次、`JSON.parse` 加保护、`logout` 集中。
2. axios **响应**拦截器 —— 401 统一登出并跳登录。

**不引入 Redux / Zustand / React Query**：7 个页面、无跨页共享的可变状态（会话列表刷新用路由重挂载即可）。为此引入状态库属于用工具规模不匹配问题规模。若后续出现跨页协同需求再评估。

### 6.3 类型

`src/types/api.ts` 按后端实际契约定义（`ChatDoneEvent`、`StageEvent`、`Citation`、`TraceStep`、`ToolCall`、`DocumentView`、`Ticket`、`ConversationDetail`…）。这不是形式主义：`done.card` 可为 `null`、`citations[].source` 在诊断热路径下可能缺失，这类可空性靠 `any` 是发现不了的，靠类型能在编译期挡住。

## 7. 设计语言

必须和原设计有明显区分（用户明确要求），同时不能沦为花哨。

| 维度 | 现状 | 新设计 |
| --- | --- | --- |
| 主色 | antd 默认 `#1677ff` | 收敛的深青 `#0f766e` 系，与"技术支持"气质相符，且和原蓝色一眼可辨 |
| 圆角 | antd 默认 6 | 10（对话气泡 14），更接近现代对话产品 |
| 背景 | `#f5f5f5` 灰 | 对话区纯白、外围极浅灰，靠留白而非边框分区 |
| 分隔 | 到处 `Card` 边框 | 去掉大部分卡片边框，用间距和弱分隔线 |
| 图标 | emoji（🧑🤖✅） | `@ant-design/icons`，emoji 在不同系统渲染差异大、也不专业 |
| 暗色 | 无 | 通过 `ConfigProvider` 的 `theme.algorithm` 支持，跟随系统 |
| 样式载体 | 满地 inline style | 主题 token + CSS Module；inline 仅留给真正动态的值 |

antd 6 是纯 CSS 变量架构，主题切换不再需要重新生成样式，暗色成本很低——这是升到 6 的一个附带收益。

## 8. 逐页设计要点

**对话（`/`）**：空态 `Welcome` + `Prompts`（示例问题从硬编码改为按角色给不同集合）。发送后立即出现 `ThoughtChain` 展示实时阶段，首个 `token` 到达时收起为一行摘要（可展开）。答案区：有 `card` 走结构化渲染，否则 markdown。答案下方 `Sources` + `Actions`。`Sender` 支持 `Attachments` 拖拽上传。

**我的知识库（`/knowledge`，新增）**：`Attachments` 拖拽区 + `FileCard.List`。显示配额用量（后端上限 50 篇 / 5000 切片）。失败文档直接展示 `error_message`，并可删除重传。内置文档同列但 `deletable:false`，不显示删除。

**历史会话（`/conversations`）**：左 `Conversations`（按时间分组），右完整对话回放。历史消息的 `meta` 里有 `card`/`citations`/`trace_id`，回放时同样渲染 `Sources`。转人工的会话保留补充消息输入框。

**内置文档（`/docs`）**：左目录（按 `category` 分组）右正文。加搜索过滤（纯前端，文档只有 8 篇）。

**我的工单（`/tickets`）**：表格 + 抽屉详情（现在点击无详情，而后端 `GET /api/tickets/{id}` 早已提供 `ai_diagnosis`/`evidence`）。

**工作台（`/workbench`，内部）**：三栏——工单列表 / 工单详情+对话 / Agent 执行链。`ThoughtChain` 替代 `@xyflow/react`，并首次展示 `tool_calls`。

**运营指标（`/metrics`，内部）**：`Statistic` + 图表。当前只有表格；`intent_distribution` 和 `by_status` 更适合可视化。**图表库选择**：不新增依赖，用 antd 6 的 `Progress`/`Statistic` 组合表达占比即可；引入 `@ant-design/charts`（体积可观）与"客户侧首屏不劣化"目标冲突，且这是内部页、优先级低。

**登录（`/login`）**：左品牌区 + 右表单。demo 账号保留（这是演示项目），但**密码不再明文写在页面上**——改为点击账号自动填充，密码不展示。

## 9. 体积与代码分割

现状 gzip 453 kB **单 chunk**：客户登录后就下载了只有内部工作台才用的 `@xyflow/react`。

措施：

1. **路由级 lazy**：`workbench` / `metrics` 用 `React.lazy`。客户角色永不加载。
2. **移除 `@xyflow/react`**：唯一用途是 Agent 链路图，改用 X 的 `ThoughtChain`。这不只是省体积——`ThoughtChain` 是纵向时间线，本就比横向流程图更适合"顺序执行的步骤 + 每步的工具调用详情"这种嵌套结构；现有实现还得靠奇偶错位避免节点重叠。
3. **`manualChunks`**：把 `antd` / `@ant-design/x` / `react-markdown` 拆成独立 vendor chunk，利用浏览器缓存。
4. **验收门槛**：客户侧首屏（登录 + 对话）gzip **不超过现状 453 kB**。这是可测量的，不是感觉。

若达不到门槛，优先砍 `react-markdown`（改用更轻的渲染或 X 的方案），而不是砍功能。

## 10. 测试策略

前端目前**零测试**（后端 215 项）。不追求覆盖率，只测最容易错且错了最难发现的地方。

**引入 `vitest`**（与 Vite 同源、零额外配置负担）。

**必测：SSE 解析器**（`api/sse.ts`）。它是纯函数，也是已经出过 bug 的地方：

| 用例 | 验证 |
| --- | --- |
| 单事件正常解析 | 基本正确性 |
| `data` 含换行 → 多个 `data:` 行 | **必须重新拼回 `\n`**（现有实现丢失） |
| `\r\n` 分隔符 | **不得残留 `\r`**（现有实现残留） |
| 事件被 chunk 边界切断 | 跨 chunk 缓冲 |
| 多字节 UTF-8 汉字被 chunk 边界切断 | `TextDecoder({stream:true})` 正确拼接 |
| 未知事件类型 | 静默忽略、不中断后续 |
| `data:` 后无空格 / 有空格 | 两种都容忍（规范只允许剥一个前导空格） |
| 空 `data:` 行 | 产生空字符串而非丢弃（它代表一个换行） |

这一组用例直接用 §3.1 里后端实测发出的真实字节作为输入，而不是我臆造的格式。

**其次**：`formatTime` / 配额计算 / `status` 到 UI 语义的映射（纯函数）。

**不做**：组件快照测试（对重构毫无价值，改样式就全红）、E2E（没有稳定环境，成本收益不划算）。

## 12. 交付顺序

前后端分开、每步可独立验证；后端在前，因为前端的阶段展示依赖它。

1. **前端 SSE 解析器**（纯函数 + vitest + 用真实字节做输入）—— 独立于一切，先修正确性缺陷。
2. **后端 `stage` 事件**：`chat.py` 改造 + `supervisor` 节点级回调 + 断连/异常/落库顺序测试。
3. **工具级 `stage`**：`ToolContext.on_stage` + `registry.execute`。可单独放弃。
4. **依赖升级 + AppShell**：antd 6 / X 2.9，三栏骨架 + 图标导航 + AuthContext + 401 拦截 + 类型定义。
5. **对话页**：`Bubble`/`Sender`/`ThoughtChain`/`Sources`/`Actions`/`Attachments`。
6. **我的知识库页**（新增，接子项目 #3 的四个接口）。
7. **其余客户侧页面**：历史会话 / 内置文档 / 我的工单。
8. **内部侧**：工作台（`ThoughtChain` 替 xyflow、首次展示 `tool_calls`）+ 运营指标。
9. **体积验收与代码分割**：对照 453 kB 门槛。

实现后的体积（gzip）：登录首包约 235 kB；登录 + 对话合计约 393 kB，低于 453 kB 门槛。
Table 等内部页组件留在各自 lazy chunk，不再打进公共包。
